You are creating a pull request for the current branch. Follow the RX team's PR conventions exactly.

## Safety Checks (do these first, stop if any fail)

1. **Not on main**: Run `git branch --show-current` — if on `main` or `staging`, STOP and tell the user.
2. **Clean working tree**: Run `git status` — if there are uncommitted changes, STOP and ask the user to commit or stash first.
3. **Pushed to remote**: Run `git log origin/main..HEAD --oneline` to see commits. If the branch isn't pushed, run `git push -u origin HEAD`.

## Gather Context

1. **Read the commits**: Run `git log origin/main..HEAD --oneline` and `git diff origin/main...HEAD --stat` to understand what changed.
2. **Find the plan**: Check `plans/` for a plan file matching this branch name — read it for context.
3. **Find the issue**: Look for a GitHub issue number in:
   - The branch name (e.g., `34869-legal-amendment-text-color`)
   - The plan file
   - The user's `$ARGUMENTS`
   - If none found, ASK the user for the issue number.

## Determine Labels

Choose labels based on the type of change. Use EXACTLY these label names:

| Change Type | Label |
|------------|-------|
| New functionality | `Type: Feature` |
| Enhancement to existing feature | `Type: Improvement` |
| Bug fix | `Type: Fix` |
| Code cleanup / refactoring | `Type: Cleanup` |
| Infrastructure / tooling | `Type: Infrastructure` |
| Urgent production fix | `Hotfix` |
| Database migration included | `Migration` |
| UI/design changes | `Style` |
| Accessibility improvements | `Accessibility` |
| Dependency updates | `Dependencies` |
| Internal (exclude from release notes) | `Internal` |

Also add area labels if applicable:
- `Storefront` — client-facing changes
- `Backoffice` — supplier-facing changes
- `Accounting` — financial/billing changes
- `Security` — security-related changes

If unsure about labels, ASK the user.

## PR Body Format

Follow the team's established format:

```markdown
Fixes #<issue_number>

**Description**
<2-3 sentence summary of what changed and why>

**User Impact**
<How this affects end users — or "No user-facing changes" for internal work>

**Instructions**
1. <Step-by-step QA instructions>
2. <How to verify the change works>

**Notes**
<Any additional context, trade-offs, or follow-up work>

---
*PR description generated by Claude Code `/pr`.*
```

## Create the PR

```bash
gh pr create \
  --title "<concise title under 70 chars>" \
  --body "$(cat <<'EOF'
<body content>
EOF
)" \
  --label "Type: Feature" \
  --label "Storefront" \
  --draft
```

- Always create as **draft** unless the user says otherwise
- Keep the title short and descriptive (under 70 chars)
- Use `Fixes #N` (not `Closes`) to reference the issue
- Add multiple `--label` flags as needed

## After Creation

1. Print the PR URL
2. Summarize: title, labels, linked issue, draft status
3. If the change needs non-trivial setup to see, post the reviewer setup as a
   PR comment (see below)
4. Remind: "Mark as ready for review when you're satisfied: `gh pr ready`"

## Reviewer Setup

When a reviewer can't see the change without data that takes more than a minute to
assemble — a rate card, a configured org, a multi-step workflow state — give them a
setup they can run, as a **PR comment**, not a file.

- Script artifacts useful to the reviewer are typically gitignored or otherwise kept
  out of the diff, so they never reach the reviewer. Whatever they need must be
  **inline in the comment**, self-contained, with no `require` of anything outside
  the repo.
- Prefer one paste-able `begin … end` block for `bundle exec rails console` over a
  sequence of UI steps. UI paths rot and are easy to get subtly wrong; a script that
  prints its result is checkable.
- End the script by printing the **URLs to open** — the reviewer's next action, not a
  description of it. Build URLs from `uuid`, not `id`: most RX show routes look up by
  uuid and an integer id 404s.
- Include the expected output so a reviewer knows immediately whether their run worked.
- Seed a **control** alongside the case under test where the change is a delta (a line
  with the feature and one without, priced identically). It turns "is this number
  right?" into a visible comparison.
- Run the block yourself before posting it. A setup script that fails on first paste
  costs more than no script at all.
